# Sketch benchmark: baseline (current `main`, pre-cascade)

Measured against the 156-fixture corpus in `LayerTests/Fixtures`, generated by
`Tools/SketchBenchmarkHarness` (`./Tools/SketchBenchmarkHarness/run.sh generate
LayerTests/Fixtures`). Rules numbers come from both `SketchBenchmarkTests` in the
"Layer iPad Pro 11 (sketch-cascade)" Simulator and the macOS harness, and agree exactly.
System 2 (Apple Intelligence) numbers come only from the macOS harness
(`./Tools/SketchBenchmarkHarness/run.sh run LayerTests/Fixtures --model`), since Apple
Intelligence calls fail in the Simulator (`layer-apple-intelligence-findings` memory note).
Raw JSON: `docs/benchmarks/baseline-report.json`.

This is the baseline the Step C and Step D benchmarks are compared against. The code under
test is `RuleInterpreter` and `AppleIntelligenceInterpreter` exactly as they stand on `main`
before any cascade work: unscored `candidates`, a separate hand-written `isCloseCall`.

## Headline numbers

| Metric | Rules only | Rules + Apple Intelligence |
|---|---|---|
| Overall top-1 accuracy | 86.5% (135/156) | 88.5% (138/156) |
| Candidate-set recall (stand-in for top-3; see below) | 85.9% | 85.9% |
| Escalation rate | 12.2% (19/156) | 12.2% (19/156) |
| System 2 accuracy on escalated cases | — | 78.9% (15/19) |
| Latency p50 / p95 | 0.04µs / 0.08µs | 392ms / 728ms (System 2 only; rules unchanged) |

The rules' own latency is in the tens of nanoseconds — pure CPU geometry, no measurable
cost. The 392ms/728ms figures are Apple Intelligence's `respond` call on this Mac, in line
with the 16 November measurement in `layer-apple-intelligence-findings` (~0.3–0.45s,
greedy sampling) and the report's own ≤1s target for a single call with no tools.

**"Candidate-set recall" stands in for top-3 recall.** Today's `candidates` is an unscored,
1–3 item list, not a ranked top-N — there is nothing to take "top 3" of yet. This number is
the fraction of fixtures where the true kind is *somewhere* in that unscored list, which is
the closest honest measurement available before Stage 1 gives candidates real scores. Once
Stage 1 lands, this is replaced with a true top-3-of-the-ranked-list recall, measured on the
same fixtures, so the two numbers are comparable but not the same thing — see the
Stage 0–1 report for the distinction made explicit.

## Confusable pairs (deliberately ambiguous fixtures only, tagged `variant: confusable`)

| Pair | Rules only | Rules + Apple Intelligence |
|---|---|---|
| button–textField | 25.0% | **100.0%** |
| checkbox–image | 100.0% | 100.0% |
| checkbox–radio | 100.0% | 100.0% |
| image–textField (see note) | 50.0% | 50.0% |
| radio–avatar | 75.0% | 75.0% |
| title–body | **100.0%** | **50.0%** |
| toggle–progress (see note) | 50.0% | 50.0% |

Two pairs from the brief don't exist as literal rule-level ambiguities today and are
approximated:

- **"card vs image"** → **image–textField**. `card` isn't a sketchable `ElementKind` yet
  (`magic-pen-expansion.md` §2), so this uses the closest real ambiguity the current rules
  have: a box in the wide band (`SketchConventions.wideBand`) where both `image` and
  `textField` are offered as candidates.
- **"toggle vs slider/progress"** → **toggle–progress**. `slider` doesn't exist either, and
  `toggle`'s ratio band (1.34–3) and `progress`'s ratio cutoff (≥7) don't overlap in the
  current rules at all — a long thin pill lands on `textField` today, not on either
  intended kind. Both halves of this pair measure the same real gap, not a shape the rules
  are actually torn about; it's included because it's one of the clearest places a scored,
  continuous rule table (Stage 1) should do better than a hand-ordered `switch`.

**The model is not a uniform win.** It fixes `button–textField` completely (25% → 100%,
matching the 16 November finding that the model wins on the rules' own close calls) and
`textField`/`image` overall, but it makes `title–body` *worse* (100% → 50%): the rules
happened to land correctly on every title/body fixture by the luck of where the chosen
widths sat relative to the 0.45 threshold, and the model overrode two of those correct
answers with wrong ones. This is the literature's "self-correction can flip a right answer"
risk (Huang et al., ICLR 2024, cited in the report), observed directly in Layer's own
corpus, not just in the literature. `image–textField` and `toggle–progress` are unmoved —
the model answered within the band of what already looked ambiguous but didn't resolve it.
Net: positive overall (+2 points), but Stage 1 and Stage 4 need to be judged on whether they
improve this pair-by-pair picture, not just the headline number.

## Confusions (expected → got), rules + Apple Intelligence

| Expected | Got | Count |
|---|---|---|
| divider | bodyText | 4 |
| radioButton | title | 3 |
| progressBar | bodyText | 2 |
| textField | image | 2 |
| toggle | textField | 2 |
| checkbox | avatar | 2 |
| bodyText | title | 1 |
| title | bodyText | 1 |
| radioButton | avatar | 1 |

**`divider` is the single biggest weak point (50%).** All four misses are the `jittered`/
`noisy` variants: `SketchAnalyzer.openForm` requires a stroke's chord to be at least 92% of
its path length to call it `.line`, and a divider's bounding box is only 2pt tall, so even a
small amount of perpendicular jitter (this corpus uses ±1.5pt jittered, ±4.5pt noisy,
uniform across every fixture regardless of its own scale) is large relative to the shape and
tips it into `.wave`, which then reads as `bodyText`. This is a real property of the
analyzer, not a measurement artefact — a uniform noise amplitude is standard practice, but
it does mean thin shapes (`divider`, `progressBar`) take a disproportionate hit. Worth
knowing before Stage 1: a continuous score for "how close to perfectly straight" would
likely help more than the escalation mechanism would, since a jittered divider isn't a
*close call* between two kinds, it's a shape that stopped looking like a line at all.

**`radioButton → title`/`avatar`** come from the same mechanism at small sizes: enough
jitter on a 24–30pt circle can break the analyzer's "ink all the way round" check, so it
stops being an `enclosure` at all and falls back to being read as a short squiggle (→
`title`, since the radio buttons in this corpus aren't near an existing title) or, in one
case, the perturbed shape still reads as round enough for `avatar`.

## Escalation blind spot (baseline-only; motivates Stage 1)

`isCloseCall` requires `candidates.count > 1`, but `SketchRequest.smallControl` — which
decides checkbox, radio, avatar and toggle — always returns exactly one candidate per
branch, even right at a dividing line. So **no small control is ever escalated today,
regardless of how ambiguous its shape is.** Every checkbox/radio/avatar/toggle miss above
(10 of the corpus's 19 escalations are the big-enclosure pairs; none are small controls) was
a confident, non-escalated wrong answer. This is exactly the problem Stage 1's scored
`ComponentRule` table and margin-based escalation trigger are meant to fix, and it's the
single clearest, most concrete baseline number to hold Stage 1 to: small-control
misclassifications should start getting escalated instead of silently wrong.

## Corpus

156 fixtures: 2 clean + 4 jittered (seed-varied, ±1.5pt) + 2 noisy (±4.5pt) for each of 16
label groups (title, body, image, button, textField, divider, toggle, avatar, checkbox,
radio, progress, screen, stickyNote, text, unknown, scratchOut) = 128 fixtures, plus 4
fixtures per confusable pair × 7 pairs = 28. All strokes come from the same generators
`SketchReadingTests.swift` and `MagicPenComponentTests.swift` use (`SketchSamples.box`,
`.wave`, `.tick`, `.cross`, `.circle`, `.straight`), plus a seeded jitter
(`SeededGenerator`, SplitMix64) for reproducibility — regenerating the corpus produces
byte-identical files.

This is the fixture set Step C and Step D are measured against; per the brief, it's fixed
from here apart from additions needed for new glyph/text kinds, which get added and then run
against both the baseline and the Stage 0–1 checkpoint so the comparison stays fair.
