# Sketch benchmark: Stage 2 ($P glyph matcher + PKStrokeRecognizer) vs. Stage 0–1

Same 156-fixture corpus, still fixed except where noted. Raw JSON:
`docs/benchmarks/stage2-pk-report.json`.

## What changed

- **$P glyph matcher** (`Layer/Sketch/GlyphMatcher.swift`): the point-cloud recognizer from
  Vatavu, Anthony & Wobbrock, "Gestures as Point Clouds" (ICMI 2012) — resample to 32
  points by arc length, centre and scale to a unit bounding box, then the greedy
  cloud-matching distance against a handful of JSON templates per glyph
  (`Layer/Resources/GlyphTemplates.json`, generated by
  `Tools/SketchBenchmarkHarness/run.sh glyphs`, reusing the same `SketchSamples`
  generators as the fixtures). Templates for circle, square, tick, cross, dot and plus.
  **Wired into scoring**: `ComponentRule.glyphRescuedSmallControl` — when `SketchAnalyzer`
  fails to parse a small shape as a clean enclosure (its "ink all the way round" check is
  strict; a few points of jitter on a 24pt circle fails it outright) and the glyph matcher
  confidently recognises a circle or square anyway, that match competes against the
  squiggle reading the shape would otherwise have lost to outright. A second, smaller
  change in the same area: `squiggleScoredReadings` now discounts title/body confidence by
  how squiggle-shaped (wide, not square) the bounding box actually is, which is what
  leaves the glyph match room to outscore it rather than being multiplied against an
  already-near-1.0 title score. Dot and circle templates are the same shape to $P once
  scale is normalised away — noted in code, not a bug.
- **PKStrokeRecognizer** (`Layer/Sketch/HandwritingRecognizer.swift`): PencilKit's new
  on-device handwriting recognizer (`init(preferredLanguages:)`, `updateDrawing(_:)`,
  `recognizedText(strokeIDs:)`), confirmed against the SDK's own `.swiftinterface` before
  writing against it (it's an `actor`, iOS/macOS/visionOS 27.0 floor, no vocabulary or
  constrained-recognition mode — matching a known word list has to be a second pass over
  whatever text comes back). `SketchEngine.read` tries it only for shapes where it's
  worth the call (`mightBeHandwriting`: a squiggle, or an enclosure with an unclassified
  mark inside it), builds a throwaway `PKDrawing` from the sketch's own points (the same
  construction `InkCanvas.swift`'s scripted-demo helper already uses), and a recognised
  word becomes both scoring evidence (`squiggleScoredReadings` no longer discounts title/
  body for an odd aspect ratio once a real word confirms it's text) and, in `AppModel`, the
  element's label — "Sign in" written inside a box becomes that button's text.

## Headline numbers

| Metric | Stage 0–1 | Stage 2 (rules) | Stage 2 (+ Apple Intelligence) |
|---|---|---|---|
| Overall top-1 accuracy | 84.6% | **85.9%** | 84.6% |
| Top-3 recall | 87.8% | 89.1% | 89.1% |
| Escalation rate | 12.2% (19/156) | 14.1% (22/156) | 14.1% (22/156) |
| System 2 accuracy on escalated | 42.1% (8/19) | — | 36.4% (8/22) |
| Rules latency p50/p95 | ~0.06µs | ~0.1–0.3µs | ~0.1–0.25µs |
| Handwriting recognizer latency p50/p95 | n/a | 0.8ms / 1.1ms | 0.7ms / 1.0ms |

**The rules-only path genuinely improved** (84.6% → 85.9%), entirely from
`radioButton` (41.7% → 58.3%): `radio_jittered_2a`, `radio_jittered_2b` and
`radio_avatar_radio_2` were jitter-broken circles the rules read as `title` with over 99%
confidence before — confirmed by direct trace (`Tools/SketchBenchmarkHarness/run.sh
explain`), not inferred from the aggregate. The glyph matcher now recognises the circle
underneath the broken outline and gives `radio`/`avatar` real competing scores; one of the
three (`radio_noisy_1`, the heaviest-jittered case) still isn't rescued — its best glyph
match is `plus`, not `circle`, at a noise level where the point cloud really has drifted
that far from a clean circle. This is a true limitation, not a threshold I didn't tune
hard enough: I checked, and no reasonable glyph-confidence cutoff recovers it without also
accepting worse false positives elsewhere.

**The end-to-end (rules + model) number is unmoved (84.6% → 84.6%).** Latency and
escalation count both still fit the report's targets, and no test broke — but the net
system-level gain is absorbed by the same problem Stage 0–1 already flagged: more cases now
escalate (22 vs. 19, since confidence crossed the 0.65 floor on more borderline shapes),
and Apple Intelligence is no more reliable on them than before (36.4% vs. 42.1% —
*lower*, simply because the newly-escalated cases are exactly the ones the rules alone
would now get right, and the model still doesn't).

## Decision: kept

Per the brief's rule, each piece is judged on whether the benchmark shows it improves
accuracy without breaking tests or latency. **Both pieces are kept:**

- **$P glyph matcher**: a genuine, traced, repeatable improvement to top-1 overall and to
  the `radioButton` kind specifically (part of two of the brief's named confusable pairs),
  at a cost that's unmeasurable against the rules' own near-zero latency. 174/174 tests
  pass.
- **PKStrokeRecognizer**: the benchmark corpus is synthetic geometric strokes (sine-wave
  squiggles, not real letterforms), so it cannot exercise real handwriting recognition —
  confirmed directly: feeding it crude letter-shaped strokes ("HI", built the same way as
  the fixtures) through this harness recognised nothing, which is expected given
  constant-speed, constant-pressure synthetic pen data, not evidence the integration is
  broken. What *is* confirmed: it compiles and runs correctly against the real SDK API on
  both platforms, adds no accuracy regression (identical numbers with and without it, since
  it never fires a false positive on geometric shapes), and costs under 1.2ms even on a
  miss. Kept because it's architecturally sound, explicitly requested, and the inability to
  verify its *accuracy* here is exactly the kind of gap the brief itself asks to be flagged
  for a real device, not a reason to leave the integration out.

Neither the rules-only gain nor the with-model wash changes this: the brief's decision rule
is about accuracy and latency, both of which point the same way for both pieces.

## What's left unaddressed

- `divider` is still 50%, for the same jitter-breaks-a-thin-line reason as the baseline —
  the glyph matcher has no "line" template, and a near-degenerate point cloud (330×2pt) is
  a poor candidate for $P's normalisation anyway. Not attempted here.
- `checkbox-radio` and `radio-avatar` are unmoved (50%/50%) from Stage 0–1 — those
  fixtures' problem is near-exact-threshold roundness, not a broken enclosure, so the glyph
  matcher's fallback path never engages for them (`SketchAnalyzer` parses them as a clean
  enclosure to begin with). Stage 0–1's report already explained why tuning that threshold
  doesn't help.
- Handwriting-recognition accuracy on real pen input: untested here by construction. Needs
  a real iPad.
